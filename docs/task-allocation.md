版本: v2.1（对齐需求 v1.1）  |  日期: 2026-08-12  |  作者: 架构师

## 1. 总体策略

- **契约先行**：api-design.md v2.1 为唯一契约；后端产出 OpenAPI，前端自动生成 TS 类型并行开发。
- **按依赖分阶段**，每阶段形成可演示闭环。
- 质量门禁（reviewer 红线 + 测试门槛）每阶段末执行。

## 3. 并行协作要点

- 前端依赖：OpenAPI 定稿后即生成 TS 类型与 API 层；阶段1 起可并行，前期用 Mock（`VITE_USE_MOCK=1`）跑通 UI。
- Agent 独立工程：后端提供 `MockAgent`（Python 脚本模拟 WS 客户端）供阶段2-3 联调与测试；Go Agent 可滞后契约冻结 1 个阶段交付。
- 后端关键路径：阶段1-3；阶段3 的 exec 状态机 + WS 回显为全项目最复杂点，优先投入。
- 每阶段末：单测报告 + 集成测试报告 + 评审意见三者齐备才进入下阶段；架构师抽查接口一致性。
- 契约变更走流程：任何接口变更由发起方在频道提出，架构师确认后更新 api-design.md 再实施，避免字段漂移。

## 4. 全局验收标准（对齐需求 US 与红线）

- 全链路：登录→建主机→Agent 上线→创建敏感命令→审批→执行实时回显→通知→审计可回放→Web 终端会话（录制回放）→定时任务自动化。
- 安全：逐接口鉴权+数据权限（默认拒绝）、审批不可绕过、凭据加密、审计不可篡改（应用+DB 双保险）、日志脱敏、并发受控、WS/Agent 身份绑定。
- 质量：单测全过+覆盖率达标（安全核心≥80%/其余≥70%）、集成测试核心场景全过、评审无 P0/P1、前端 TS 类型与 OpenAPI 一致。
